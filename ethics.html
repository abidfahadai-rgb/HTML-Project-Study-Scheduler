A Considered Approach

Ethics and Privacy Reflection

On the responsibilities that come with handling a student's personal study data.

The Premise

Even a small student-built application is, in a meaningful sense, handling personal data. Coursework titles, deadlines, and notes may reveal that a user is struggling with a subject, working ahead, or making private observations they would rather keep to themselves.

Building this scheduler responsibly meant thinking about three things: who can see the data, what data we collect in the first place, and how we handle what users put in.

Features Supporting Ethical Data Use

Restricted access through login

The scheduler and summary pages are both guarded by a requireLogin() check. A user who reaches those URLs without an active session is redirected back to the login screen. Each task also carries an owner field, so two accounts in the same browser cannot see each other's tasks.

Input validation and text escaping

Every form input is validated before being accepted. Empty required fields are rejected, dates in the past are refused, and clear error messages are shown to the user.

Every piece of user-typed text is passed through an escapeText() helper before being written to the page. This means a user cannot accidentally or maliciously store HTML or JavaScript that would later run when their tasks are displayed.

Honest error messages

When something goes wrong - a wrong password, an invalid date, a missing field - the user is told plainly. But the login form does not say whether the username exists or just the password is wrong, because telling the user that would help attackers guess valid usernames.

Features Supporting Data Privacy

Data minimisation

The application collects only what it needs. Username and password for authentication; for tasks, only title, course, date, description, and optional notes. No email, no real name, no phone number, no date of birth, no location is asked for. The less we collect, the less there is to lose.

Local-only storage

Every piece of data the application stores - accounts, sessions, and tasks - lives in the browser's localStorage. Nothing is sent to a server. No analytics. No tracking. When the user clears their browser data, the application's record of them is gone.

User control

Users can delete any task at any time. The deletion is confirmed first with a popup, to prevent accidents. They can also log out, which clears the session immediately. There is no hidden retention and no "soft delete".

Acknowledged limitations

In the interest of honesty: this scheduler is a learning project. Passwords are stored in plain text in localStorage, which is not secure. A real application would hash passwords with a strong algorithm like bcrypt, send them over HTTPS, and keep them on a server with proper session tokens. None of these are possible in a simple client-side project, so the README, this page, and the source code itself all say so plainly. Being honest about limitations is itself a privacy practice - users cannot consent to risks that are hidden from them.

Worked Examples

  • Required fields, but no surveillance fields. The task form asks for things the user benefits from recording. It does not ask where they study, when, or for how long.
  • Owner-stamped records. Every task carries the username of its creator. Users cannot see each other's tasks even when they share a browser.
  • Confirmation before deletion. A popup asks the user to confirm before any task is deleted.
  • Text escaping on display. A task titled <script>alert(1)</script> appears on the page as text, not as a running script.
  • Honest about plain-text passwords. This page, the README, and the source code all state that the login system is for learning purposes only.

A Closing Thought

Good privacy practice rarely looks like a feature. It looks like a question that was asked early and answered carefully: do we really need this? If the answer is no, the responsible choice is also, very often, the simpler one.
